## Contradictions and stale material found

1. `tee-proxy/README.md` names flat direct-endpoint config keys; `config.example.toml` and `pkg/config/config.go` use `[direct] enable`, `api_key`, `api_key_variable`, `api_key_optional`, `max_body_size`.
2. `flare-smart-contracts-v2/main` does not contain the FCC Solidity contracts referenced by current specs/deployments. Contract behavior is cited to `flare-specs` and generated ABIs, not guessed.
3. Some orderbook docs describe state as entirely in-memory, but current source optionally persists balances to unsealed JSON; orders/history remain volatile and persistence is disabled by default.
4. Weather-insurance comments/UI describe private terms, but its relay publishes the decrypted terms as calldata.
5. FAssets demo redemption default messaging implies completion, but source only calls a read-only verifier and never the AssetManager default method.
6. FAssets demo chain parameters conflict with a singleton Flare client and Coston2/`testXRP` proof endpoints.
7. Current relay/scaffold-pinned signing includes chain-ID domains that the checked-out node/proxy heads predate; “clone latest everything” is not a valid integration recipe.

## High-severity design traps recorded

- Claimed sender without a wallet signature in direct orderbook actions.
- Proxy API key treated as user identity.
- Volatile private balance/nonces while on-chain custody persists.
- Random machine selection for stateful multi-step lifecycles.
- Replayable signed result/action ID in weather private-buy relay.
- Secret inputs copied into public settlement calldata.
- `uint256` values narrowed to `uint64` in reference accounting.
- Race-prone event watcher without historical backfill/timeout.
- Smart Account examples with zero executor compensation.
