## Objective

After this milestone a developer can install the kit and drop a working **vault
catalogue**, a **deposit** card and a **withdraw** card into their own React app,
and a person can deposit real FXRP into a real ERC-4626 vault on Coston2 — testnet
first — receive real vault shares, then withdraw through the vault's **actual
delayed lifecycle** and later claim the assets, seeing the **honest share amount**
at the vault's current exchange rate, the **exact minimum** protected under
slippage, the **real fee** and any **cap or pause** the vault enforces, and every
approval and every step on an explorer. Vaults are the third application-layer
capability in the DEX bucket, built on two live Coston2 vaults with **materially
different withdrawal models**, and they reuse the durable operation lifecycle M1
forced into being and the surface anatomy M5/M6 established.

## The venues — probed, live, and fundable (no re-probe needed to build)

M7 grounds itself on the read-only probe already run (evidence file above).
Two ERC-4626 vaults are live on **Coston2**, both holding the FAsset the DEX
config already carries — **FTestXRP** `0x0b6A3645c240605887a5532109323A3E12273dc7`,
6 dp:

- **Firelight** `0x91Bfe6A68aB035DFebb6A770FFfB748C03C0E40B` — a **self-share**
  ERC-4626: the vault token itself is **stFXRP** ("Staked (test) FXRP", 6 dp).
  Exchange rate 1:1 today (`totalAssets == totalSupply == 14994061`), deposits
  open (`maxDeposit` unbounded). Withdrawal is **period-based**: `withdraw` /
  `redeem` create a request bound to `currentPeriod` (333) with **no immediate
  transfer**; assets arrive only via `claimWithdraw(period)` after
  `currentPeriodEnd`. Periods are **1 day** (`nextPeriodEnd − currentPeriodEnd`).

- **Upshift** `0x24c1a47cD5e8473b64EAB2a94515a196E10C7C81` — a **separate-share**
  vault (`ITokenizedVault`): the LP/share token **vFXRP**
  `0xe084F7328DDaB082a139b880782dCC424d20a1DB` (6 dp) is a distinct contract.
  Withdrawals not paused; **two exit routes** — `instantRedeem(shares, receiver,
  holder)` burns shares for immediate assets at `instantRedemptionFee`, or
  `requestRedeem → lagDuration (1 day) → claim(year, month, day, receiver)` at the
  lower `withdrawalFee`, keyed to a **calendar epoch** (`getWithdrawalEpoch` →
  `2026-08-12`). A `maxWithdrawalAmount` cap (10,000 FXRP) and `withdrawalsPaused`
  are first-class vault state.

Addresses live in `@flare-kit/contracts`, never hardcoded elsewhere. The signing
account `0xA4b05cdB545FA7CA12Be9f866d64E8A843A31Bd9` holds **23.80 FXRP + 97.82
C2FLR** — funded for a real deposit → withdraw-request → claim round trip on both.

## The vault model, and the honesty it forces

An ERC-4626 vault is a **share wrapper**: `deposit(assets, receiver)` mints shares
at the current `convertToShares` rate; `previewDeposit` / `previewRedeem` quote it.
That half is standard, immediate, and cross-venue safe. **The withdrawal half is
not, and it is the load-bearing surface of this milestone.** Both vaults make
withdrawal a **request → wait → claim** lifecycle, and the two do it differently:

1. **A withdrawal request is not a withdrawal.** Firelight's `redeem` returns and
   emits, but transfers nothing; Upshift's `requestRedeem` likewise. Rendering
   either as "assets received" is exactly the `submitted`-as-`succeeded` failure
   the hard rules forbid. The WAITING state (period end / calendar epoch) is
   explicit and durable; CLAIMABLE is a distinct state; only `claimWithdraw` /
   `claim` **success** → CONCLUDED, carrying the **actual** assets returned.

2. **The exit route is a real, fee-bearing choice.** Upshift's instant route is a
   *different call at a higher fee*; the delayed route is cheaper but waits. The
   kit presents both honestly and never collapses them, and never hides the fee.

3. **The two vaults share a lifecycle, not an ABI.** Self-share + period vs
   separate-LP + lag/calendar-epoch + instant are materially different contracts.
   Per the M6 lesson already recorded (`adds are venue-specific`), the shared
   abstraction is the intent → plan → state lifecycle behind a `VaultAdapter`, not
   one ABI. Building both from the start forces the abstraction to be correct.

4. **Pause and cap are protocol-availability states, not user errors.**
   `withdrawalsPaused` and `maxWithdrawalAmount` are read live and gate the plan
   with their own reasoned states.

## Requirements

- **M7-R1 — `@flare-kit/contracts` gains the vault registry; addresses from the
  registry only.** A network-keyed vault registry (`vaults.ts`) carries, per
  network, each vault's address, protocol (`firelight` | `upshift`), asset key,
  share-token identity (self vs separate LP address), and a **`withdrawVerified`**
  flag (Coston2 `true` after the M7 live run; any network without a live run
  `false`). Coston2 addresses are those the probe verified. Mainnet carries the
  Upshift vault `0x373D…dEA28` (reads only until verified); Firelight mainnet is
  absent → declared-unbuilt-until-known. No address is hardcoded outside the
  registry.

- **M7-R2 — `@flare-kit/core` deposit + withdraw operations over one adapter.**
  Immutable intents — `DepositIntent` (vault, amount, slippageBips, deadline,
  recipient) and `WithdrawIntent` (vault, an **absolute** share amount, an
  explicit **route** = `delayed | instant` where the vault offers a choice,
  slippageBips, deadline, recipient) — resolve through a `VaultAdapter`
  (Firelight / Upshift) to an **unsigned plan** (an `approve` step only when the
  asset — or, for Upshift instant, the LP token — is actually short, then
  `deposit` / `withdraw|redeem|requestRedeem|instantRedeem`) → **execution** →
  canonical states, with typed errors distinct for **paused**, **cap-exceeded**,
  **insufficient-balance**, **share/slippage-exceeded**, and **expired-deadline**.
  It reuses the M1 lifecycle engine and **walks the `states.ts` table** (a
  reconciler never jumps states — the `applyTransition` silent-drop hazard).

- **M7-R3 — the withdraw lifecycle is durable and self-reconciling.** A withdrawal
  request persists its evidence (vault, protocol, share amount, route, the
  concrete **claimable-at** — Firelight `period` + `currentPeriodEnd`, Upshift
  `year/month/day` + `lagDuration`), and on app open **reconciles against the
  chain** (`withdrawalsOf` / `isWithdrawClaimed` for Firelight; the pending
  redemption read for Upshift) — states are chain state, not session state; there
  is no Resume button. The lifecycle is **PRE-PLAN → (approve) → submitting →
  requested/WAITING → CLAIMABLE → claiming → CONCLUDED**, plus the terminal
  refusal states; the instant route is **PRE-PLAN → (approve) → submitting →
  CONCLUDED** in one step.

- **M7-R4 — the quote is honest, minimums are exact, fees are real.**
  `vault-quote.ts` reads live `convertToShares` / `previewDeposit` (deposit) and
  `previewRedeem` / `convertToAssets` + the vault's fee (withdraw), the signer's
  share balance for the position, and computes: expected shares (deposit),
  expected assets net of the route's fee (withdraw), and the protected minimum
  `amount · (10000 − slippageBips) / 10000`, shown at full precision in the mono
  face beside the expected amount. An unknown value renders as `—`, never `0`. A
  quote carries the time it was read; a rate move between quote and execution that
  trips the minimum on-chain renders as **share/slippage-exceeded**, a distinct
  state, not a kit failure. Fee/cap/pause come from live reads, never assumed.

- **M7-R5 — approvals are never hidden.** The ERC-20 allowance is read for the
  deposit asset (and, for Upshift instant/withdraw, the LP token where the vault
  pulls it); the plan includes an `approve` **only** when short. Every approval is
  its own step with its own transaction, and the full sequence is stated before
  the first signature (R-LIQ-106); a pre-approved leg shows no step.

- **M7-R6 — real-first; the mock copies observed behaviour.** `mock-vault.ts` is
  written **only after** the real path and reproduces observed exchange rates, the
  share mint/burn math, the two withdraw models (period + calendar epoch), fees,
  cap and pause, and the failure shapes. Mock mode is explicit and labelled, never
  a fallback triggered by a failure, and it **refuses to answer any vault, route
  or state it never observed** rather than returning a plausible zero.

- **M7-R7 — VaultCatalogue (LIQ-01).** Lists the configured vaults for the active
  network with, per vault: protocol identity, deposit asset, share model
  (self-share stFXRP vs separate-LP vFXRP), current exchange rate, live
  fee(s), the exit modes (instant/delayed), and any **paused / cap** state — each
  from live reads with a SourceChip, `—` where unknown, never a guess. A vault
  configured but not `withdrawVerified` on this network shows its reads but its
  withdraw action is a **declared-unbuilt** affordance (present, disabled,
  reasoned), never a plan that could misrender.

- **M7-R8 — DepositCard (LIQ-02).** One "you deposit" leg for the asset and one
  "you receive" leg for the expected shares at the live rate; the exact minimum
  under slippage; a plain-language statement that shares are a claim on the vault
  whose asset value moves with the vault. The approve(s) and `deposit` render on
  the operation spine as the real steps they are (M7-R5). Reuses the established
  card anatomy — no new per-surface design artifact.

- **M7-R9 — WithdrawCard (LIQ-03), durable timeline with a live countdown.** Reads
  the signer's live share balance on open (self-reconciling, no Resume button),
  offers **partial withdrawal by percent** (25 / 50 / 75 / 100 and an exact entry,
  reusing `PercentPills`), and — where the vault offers both — an explicit
  **route choice** (instant, showing its higher fee and immediate effect; or
  delayed, showing its lower fee and the wait). The request → wait → claim
  lifecycle renders on the operation spine with a **durable timeline**: WAITING
  shows the concrete claimable time (Firelight `currentPeriodEnd` / Upshift
  calendar epoch) with a **live countdown**, flips to a **CLAIMABLE** badge when
  reached, then a Claim step → CONCLUDED with the actual assets received. When
  there is no share balance it shows an honest **no-position** state; when the read
  is unavailable it shows **unavailable**, never a confident "no position" (the M6
  F1 rule).

- **M7-R10 — network is configuration; unverified write paths are gated, not
  faked.** One code path serves Coston2 and mainnet; only the registry changes.
  Testnet first. Reads run on any configured network; a vault whose withdraw model
  is not live-verified on the active network (`withdrawVerified === false`) never
  emits a withdraw/claim plan — it renders the declared-unbuilt affordance (the M6
  F2 precedent: never sign approvals then revert on an unverified venue).

- **M7-R11 — reuse, files < 300 lines.** Reuse `SwapLeg` for the deposit/receive
  legs, the `OperationTimeline` spine, `PercentPills`, and `Panel` / `Button` /
  `AssetLogo` / `EvidenceChip` / `DetailRow` / `Note` / `SourceChip`. The pure
  state→chrome mapping for each card splits into `deposit-card-state.ts` /
  `withdraw-card-state.ts` at the same seam `swap-card-state.ts` sits on. The
  per-card chrome duplication the M6 review flagged (percentOf, Cta/CardNote,
  PRE_PLAN/IN_FLIGHT/CONCLUDED) is **homed once** here rather than re-declared.

## Out of scope (M7)

- **Yield / APR / TVL figures** — appear only when sourced (R-LIQ-104); no vault
  read on Coston2 supplies a trustworthy APR, so none is rendered. A later
  milestone with a real yield source may add it.
- **Mainnet live verification** — the mainnet Upshift vault is configured for
  reads only; its withdraw path is declared-unbuilt-until-verified (M7-R10). A
  mainnet live run is its own follow-up, exactly as M6's mainnet add was.
- **Firelight `mint` / Upshift share-target deposit** (specify shares, compute
  assets) — the asset-in `deposit` path is the committed real-first flow; the
  share-target variant is a later addition, not a second implementation now.
- **Smart-Account-mediated vault actions** (deposit via XRPL Personal Account) —
  that belongs to the Smart Accounts milestone, which owns the FDC-proof relay.
- **Blocklist / rescue admin operations** on the Firelight vault — operator
  surface, not a consumer capability.

## Acceptance criteria

- **AC1** — a real **deposit → withdraw-request → claim round trip** is executed
  and recorded on Coston2 for **both** vaults: the deposit approval tx(s) and
  `deposit` tx; the withdraw approval (where pulled) and the request tx
  (`withdraw`/`requestRedeem`); after the period/epoch, the `claimWithdraw`/`claim`
  tx — each with its explorer link, and the network + addresses + the share and
  asset balances before/after noted as evidence. Upshift's **instant** route is
  additionally driven once end-to-end.
- **AC2** — the rendered deposit quote (expected shares) equals the value computed
  from the on-chain rate for the same inputs, and the **predicted shares match the
  actual shares minted** (the share-balance delta AC1 records) within rounding; the
  withdraw quote's expected assets match the **actual assets claimed** net of the
  vault fee; a rate move that breaches the minimum reverts and renders as
  **share/slippage-exceeded**, never as success or a kit failure.
- **AC3** — a **withdrawal request is never rendered as assets received**: WAITING,
  CLAIMABLE and CONCLUDED are each distinct, reachable states, and CONCLUDED alone
  carries the actual assets. `mock-vault.ts` **refuses** any vault, route or state
  it never observed (a plausible zero is a loud error).
- **AC4** — the exit-route choice is shown with its real fee (instant higher,
  delayed lower); `withdrawalsPaused` renders **paused** and `maxWithdrawalAmount`
  renders **cap-exceeded** as first-class states, never as user error; each
  approval is its own step and a pre-approved leg shows none.
- **AC5** — Gallery, both themes, states reachable from props: VaultCatalogue
  {list, vault-paused, withdraw-unverified/declared-unbuilt, read-unavailable},
  DepositCard {quote, needs-approval, approving, depositing, success,
  cap-exceeded, insufficient-balance}, WithdrawCard {no-position, unavailable,
  position, route-choice, needs-approval, requesting, waiting (countdown),
  claimable, claiming, claimed, instant-success}. Computed-style + a11y verified
  (contrast composited with opacity, focus, target size), the M4-R12 method.

## Verification

`packages/core/scripts/live-vault.mjs` drives the whole path through the kit for
each vault — read rate/preview + allowance → `buildDepositPlan` → sign approval(s)
and `deposit`; read the share balance → `buildWithdrawPlan` (delayed) → sign
approval (where pulled) and the request; wait the period/epoch; reconcile
`isWithdrawClaimed` / pending-redemption → `buildClaimPlan` → sign the claim; and
separately drive Upshift `instant` once — recording every tx hash, explorer link,
and the share and asset balances before and after. It signs with its own key
(`privateKeyToAccount(secrets.evm.privateKey)`), the headless path, exactly as
`live-swap.mjs` / `live-liquidity.mjs` do; the browser surfaces sign through the
host's connected wallet via `onSubmit` and never hold a key. Because the withdraw
wait spans a **1-day** period/lag, the live run is **two-phase** (request, then
claim after the boundary) and the evidence file records both phases with their
timestamps; a same-day claim is only possible if the request lands before the
current period/epoch boundary, otherwise the claim phase runs the next day.
`pnpm build && pnpm typecheck && pnpm lint && pnpm test` green, shown with output.
The gallery drives every AC5 state and is screenshotted in both themes.
