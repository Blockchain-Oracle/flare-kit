## Gate

Run from the repository root. Exit codes captured per command rather than
through a pipe — `pnpm lint` is `eslint .` directly, so piping to `tail` would
report `tail`'s status instead.

```
pnpm build --force       → 0    Tasks: 6 successful, 6 total    Cached: 0 of 6
pnpm typecheck --force   → 0    Tasks: 12 successful, 12 total  Cached: 0 of 12
pnpm lint                → 0    (eslint ., no output)
pnpm test --force        → 0    Tasks: 12 successful, 12 total  Cached: 0 of 12
```

`--force` is not decoration. `turbo.json`'s `inputs` for `build`, `typecheck`
and `test` list `src/**`, `app/**`, `components/**` and `test/**` but **not
`lib/**`**, so a change confined to `apps/app/lib/` does not invalidate any
cache and an unforced gate can report green without executing the changed code.
`apps/site/lib/` has the same hole. Recorded here as an open defect; it is not
fixed by this plan.

### A failure that was not one

An earlier `pnpm test --force` reported `Tasks: 3 successful, 8 total`, exit 1,
with `Failed to start forks worker`, `Timeout waiting for worker to respond` and
a `@flarekit-dev/react:build` `ELIFECYCLE`. No assertion failed anywhere in that
output. It was resource starvation: several forced turbo runs and a dev server
competing for the same machine. `@flarekit-dev/react` builds clean on its own,
and re-running with `--concurrency=1` gives the 12/12 above. Recorded because a
red gate that is really a busy machine is worth being able to recognise twice.

## The tab icon, precisely

`apps/app/app/icon.svg` is byte-identical to `apps/site/app/icon.svg` and to
`brand/flare-kit-mark.svg` (verified with `diff` against each). Next emits it
into the head:

```html
<link rel="icon" href="/icon.svg?icon.332r-9wxlpcjg.svg" sizes="any" type="image/svg+xml"/>
```

A direct request to `/favicon.ico` still returns `404`, and that is correct
rather than a leftover: with a `rel="icon"` link present the browser requests
`/icon.svg` and never falls back to the legacy path. The console is clean
because nothing asks for `favicon.ico`, not because a `favicon.ico` was added.

## Focus, checked because it was doubted

The rail showed no focus ring in either screenshot. It is not a defect: no
element was focused when they were taken. The kit already declares the
treatment, and never lets a surface suppress it:

```css
/* packages/react-ui/src/styles.css — "Never suppressed: 2px primary ring at
   2px offset (DESIGN.md accessibility bar)." */
.fk :focus-visible { outline: 2px solid var(--fk-primary); outline-offset: 2px; border-radius: 3px; }
```

`.fk` is on `<body>`, so every focusable thing in the app — rail links, the
network selector — is a descendant and inherits it. Nothing in the app sets
`outline: none`. The rail's 12px padding clears the 2px ring at 2px offset, so
`overflow-y: auto` does not clip it.

This audit found the opposite defect: `apps/app/app/globals.css` had grown its
own `:focus-visible` rule, a second copy of the kit's minus the `border-radius`.
Removed. The app declares no focus treatment of its own.

into `packages/react-ui/src/BrandMark.tsx` and are exported from the package

## Known gaps carried forward

- **No account control.** `TopBar`'s `account` slot is empty. The connect flow is
  R-APP-010/011/012 and belongs to plan 2. A Connect button that cannot connect
  would be a fabricated affordance, so there is none. R-APP-004 is not fully
  satisfiable until then.
- **Every screen that renders kit components must be a client component.** The
  `@flarekit-dev/react-ui` barrel re-exports `@flarekit-dev/react`, which builds
  a `createContext`, so importing it into a Server Component fails the build.
  This forced `'use client'` on `apps/app/components/unbuilt.tsx` and on
  `apps/site/components/footer.tsx`. It constrains where server data fetching
  can sit in plan 2.
- **`turbo.json` `inputs` omit `lib/**`**, as above.
- **`.app-unbuilt` is capped at `max-width: 560px`** — a placeholder. Panel width
  touches spec open choice 3, which is undecided.
